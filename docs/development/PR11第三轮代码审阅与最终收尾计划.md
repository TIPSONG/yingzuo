## 4. 架构约束与逐项实现方法

### C01：统一图的保存与导出边界

当前任务快照的 API 脱敏可继续使用，但不能把它当成所有图已经安全保存。`tasks.exportPackage` 读取原始 `t.graph` 后直接 buildPackage；buildPackage 的 strip 只认识已有 `__yz_credential__:` 占位。因此首次打开并输入密钥、尚未运行/存模板的图，仍会导出明文。直接 `templates.import` / 内置导入也直接 repo.create，原始敏感值并未经过 securedGraph。

实现一个共享 GraphStoragePolicy，分别提供“内部保存”和“对外导出”。由所有草稿、关闭归档、模板创建/版本、普通 JSON 导出、图包导出和修复副本导出调用。边界不能依赖“用户先运行一次”。

- 根据节点字段定义、已知字段和嵌套子图识别敏感 widget；API 编译可辅助，但离线保存也要有明确策略。未序列化为执行节点的 UI 字段也不能仅因为 API 图里没有就原样带走。
- 内部文件保存凭据引用；系统加密存储不可用时返回可操作错误，保留内存修改，不能悄悄明文落盘或将必需值清空后继续。
- 导出移除真实值和本机凭据标识，并提供需要重新填写的字段清单；普通提示词、图结构和模型选择应保持完整。
- 保存策略只生成磁盘副本，避免改变活跃画布 revision、错误替换用户提示词或把占位当成普通提示文本。重新加载及提交按引用在内存恢复，缺凭据清楚提示。
- 旧文件的处理提供迁移/检查记录，不直接覆盖用户外部 JSON；备份前也执行同一内部保存政策，不能继续把已知原始密钥复制进新备份。

开发检查：用虚构密钥分别走“首次输入→自动保存→关闭重开→普通导出→图包导出→本地模板导入→在线模板导入→备份”，递归查实际生成文件。含未连接节点、子图、离线、系统凭据不可用和新机器缺凭据；正常文本保留，任务可在内存解析后提交。不用仅检查 helper 返回值代替生产调用链。

### C02：维护写前日志与启动阻断

现有 holdAfterFailure 只在能进入 finally 的失败路径写盘。若进程在 `plan.apply` 修改 Git/Python 环境后被结束，最后事件可能仍是 staging；holds 文件没有记录，backup_ref 尚未登记。下次启动不会从 env_transactions 或恢复 journal 推导阻断，可以继续启动/生成。

将维护状态改为写前持久化协议：备份完成即保存 backupRef；进入 apply 前保存 `apply-started`、txnId、roots、原服务状态和备份引用；恢复动作同样写前登记。只有 apply+check 或 restore+verify 完成，才标终态并解除对应阻断。不要用 finally 是否执行作为恢复依据。

启动时在调度器/服务命令可用前读取事务与 journal，重建 holds；无法证明已完成的 apply/restore 保守留在待恢复状态。区分“尚未修改环境，可取消登记”与“已经可能修改，需恢复/检查”；不自动重放 Git checkout、pip 或未知 apply。holds 格式损坏或非数组不能当成空清单。

backupRef 与 roots 要持久化到事务记录；备份清理保护 holds 与未完成事务用到的备份，不能因 phase 被统一写成 failed 就认为可清理。释放条件绑定事务/备份/受影响目录，C03 的服务 gate 与队列租约使用同一状态源。

开发检查：独立子进程和临时环境在 backup 后、apply 第一项写入后、restore 中间被强制结束；重新组装服务后先观察阻断、备份保留与队列状态，再执行继续/回退。测试正常完成不会永久阻断，且恢复另一份无关备份不会解除当前事务。

### C03：环境操作统一检查顺序

MaintenanceTransaction 先查 services，再拿锁和等待本应用任务完成，最后根据旧 services 停后端。这可能相隔很久，期间 owned ComfyUI 也可能收到原生画布/其他客户端任务。guardedRestore 也存在检查在等待前的问题。main 对 startComfy 的 gate 检查则位于环境锁外，等待锁期间新产生的 hold 不会被重检。

统一环境入口：取得环境锁 → 在锁内检查 gate → 取得提交暂停租约 → 等待本应用 active 与 starting 完全结束 → 重新检查后端 ownership 与所有队列来源 → 决定停止/拒绝 → 执行变更。启动服务、移动模型、继续恢复和更新均使用同一 guard，不分别复制不完整的流程。必要的初步探测可用于提示，但不能作为最终执行依据。

停止前如果后端有其他来源任务或无法确认状态，返回阻止原因，保留它们，不调用全局 interrupt。启动 gate 必须在实际取得环境锁后再次检查。不要声称“再次 GET /queue”能给出服务端原子独占保证；若后端没有合作协议，应明确维护时需独占后端的边界，失败时保持可恢复状态。

开发检查：等待本应用任务结束期间出现外部任务；启动请求等锁时维护失败产生 hold；后端查询失败；服务所有权改变；starting 查询还未完成。断言实际 stop/start/apply 调用次数和最终租约状态，不能只断言错误文案。

### C04：独立应用恢复模式与可回退的文件事务

应用恢复失败时 entry 无条件加载 main；main 会 ensureLayout、导入旧数据、Database.open、组装服务，随后启动任务恢复和下载/更新组件。暂停绘图与维护不足以阻止模板、参考关系、数据库迁移等普通写入。尤其数据库已 preserve 但 swap 失败时，普通启动可能在目标位置新建数据库，继续恢复又会遇到“目标仍存在”。

entry 先决定 normal / recovery。恢复失败、标记损坏或仍有未完成 journal 时进入独立 recovery bootstrap：只读取恢复记录、显示错误、提供继续/回退/退出与日志定位；不要初始化普通写服务、迁移数据库、自动保存、下载恢复或更新任务。恢复界面必须在业务数据库无法打开时仍可用。继续/回退使用同一 journal，成功校验并清除标记后才重新进入 normal。

同时修 RestoreEngine.rollback：`_carry` 从 scene 搬出的模型、input/output 等排除内容，可能已经位于 staged 或新 target；回退前要按 journal 搬回原 scene，再把 scene 恢复为 target。否则虽然模型仍保存在 .yz-failed 里，恢复后的旧环境却缺模型与输出。记录每个 carry 的实际位置和步骤；冲突保留双方、停止并提示，不能覆盖唯一内容。数据库及 WAL/SHM、原目标不存在、回退再次中断也使用可重入的步骤，不能依靠一轮 rename 全部成功。

开发检查：按 stage/preserve/carry/swap/verify 分别注入失败，含目标数据库已搬走；进入 recovery 后确认没有新数据库/迁移/普通写入，继续和回退均能启动正确数据版本。环境样本包含被排除的模型/input/output；回退后在原路径核对原字节和 hash，不以“某个失败目录里还能找到”作为成功。

### C05：模型移动的同一套保护覆盖恢复与正常执行

启动 recoverModelMoves 已比上轮安全，但只看本应用 activeTasks，没有核对现有 ComfyUI 中的外部任务。正常跨盘移动算 srcHash→复制→校验 tmp→rename→直接删除源，没有源内容变化的最终检查；“重启恢复”路径有的检查，正常成功路径也必须有。

启动恢复采用 C03 的统一环境 guard，不能仅因为本应用没有 active 就修改或删模型。暂停后等待 starting 消退；后端外部任务存在/未知则推迟，保留 journal。正常跨盘复制后重新检查源身份与 hash，变化则保留新源和复制结果并记录 conflict；目标存在不同内容不得覆盖。对当前支持的平台，目标提交采用拒绝覆盖的操作/策略，实际能力不足时明确失败并保留现场。

删除 tmp 也要证明它是该事务的可丢弃内容；已有不同 tmp 不因 destOk 就盲删。源、目标与临时文件都核对登记根、类型和实际路径，链接边界沿用现有模型保护。不自动替用户选择冲突的一份。

开发检查：启动时只有外部后端任务；复制期间源被另一写者替换；提交前出现目标；tmp 被替换；仅 tmp 为完整唯一副本；任务 starting 尚未结束。测试隔离文件的 hash、journal 与保留位置，不操作真实模型。

### C06：表单版本、缓存、约束与任务身份闭环

目前左侧主表单已接入，不再列“没有主表单”这个旧问题。剩余问题有三条调用链：

1. accept 只在 activeId/connection/view 改变时清理 formPanel；同一标签 saveForm→setTemplateVersion→notify 不会刷新面板。新的 fields/标签/范围保存成功后，当前面板仍可沿用旧 schema。
2. formDraft 仍读 repo.current(id)，会把固定 v1 的旧图配到已更新 v2 的表单编辑器。
3. 面板直接 api.applyParameters，不传 expectedRevision，也不调用自定义 constraints 校验；HTML min/max 不会阻止 change 处理器提交越界值。tasks.run 仅当传 formValues 才 applyCustomForm，普通按钮没有传，所以不能依赖它兜底。

用 `{tabId, revision, templateId, templateVersionId, schemaVersion}` 作为面板缓存身份。模板保存/重绑或图变化后，失效缓存并重新映射；只接受所属标签与版本的异步响应。formDraft/checkMapping/rebind 以标签固定版本为起点，用户明确选择升级才换到最新版。

把字段约束校验放到共享纯函数，并在主进程表单写回入口执行类型、有限数字、整数、范围、选项及必要步长检查。前端只负责即时提示；不能只设置 HTML 属性。所有写回带 expectedRevision 和表单版本，图/绑定变化时拒绝并刷新。最后运行、润色和批量在编译后校验实际表单值/失效映射，不能因为没有 formValues 就跳过。原生画布改图时，不应被表单缓存强行写回旧值。

普通、批量、仅润色、采用后生成及资源快捷使用的快照统一记录 templateVersion/formVersion 与实际使用值。目前 runBatch/enhance 未沿用普通 run 的 formIdentity；同时普通 run 的身份不应仅因表单为空就丢掉模板来源，以免模板首图自动缩略图漏接。独立副本应保留独立表单配置或明确解除绑定，不能悄悄用最新版代替。

开发检查：同一标签保存新的中文名/分组/范围立即显示；A(v1)/B(v2) 不串表单；v1 表单设置仍从 v1 开始；迟到响应不能覆盖新版；越界/错误类型不修改画布、不入队；修改图后旧表单回写被拒绝；按钮/Ctrl+Enter/批量/润色保留同一版本身份。覆盖实际 UI 调用与主进程入口，不只 mapFormTargets 单元测试。

### C07：图包往返不丢语义

parsePackage 创建了 nodeIds 却没使用，只检查 nodeId/input 的字符串格式；不存在节点或错误输入也能通过。importPackage 只保存 !missing 的关系，用户看到一次“缺失素材”提示后，它不再进入 refsForRun 的缺失检查，运行可能沿用旧的后端文件名。template.formSchema 也只在返回值备注中出现，未用于新工作副本。

包内关系应包含明确的实例 scope、nodeId/input、内容 ID、hash/大小与存在状态。对根图和嵌套子图逐项验证槽位存在、用途可接受、无重复冲突；不能仅凭编号同形就接受。离线无法确认自定义节点输入契约时标待核实，连接后诊断，不能假装验证完成。先整体校验，再导入文件、创建标签并提交关系，失败保留原工作区。

missing 项也恢复为缺失关系；不改成空清单、不过滤后继续生成。运行仍阻止并定位对应槽位，用户重新选择或明确移除后才解除。图中裸露的 LoadImage 后端路径应与 manifest 区分：它不代表素材已经随包导入。

将 formSchema 作为新独立工作副本的可编辑配置恢复，不将旧机器 templateId/versionId 当成本机可用的外键。可建立明确的新本地模板版本或独立表单记录，但原来源 ID 仅用于追溯，不能误绑定本机同名旧模板。默认不新增模板库条目时，独立表单必须被 workspace/formProvider 支持。关闭→重开、复制、备份→恢复沿用同一配置与关系规则。

检查单项/总大小上限在读取前生效；不静默 slice 截断 manifest，不生成自身无法导入的包。当前 50 MB/300 MB 约束可保留，无需改包格式到另一套产品功能。

开发检查：含实际 PNG 的包在全新临时数据根往返；缺失素材仍存在于关系与诊断，无法生成；错误 node/input/重复槽位/子图同号节点/损坏 hash 整体拒绝；导入后的表单仍可编辑运行；外部 templateId 不串到本地模板；导入失败没有留下半个标签或关系。

### C08：Worker 生命周期与剩余同步路径

已有 worker 元数据/缩略图/哈希/复制及打包验证应保留。不要为了完成状态将它们重写。当前 close 只清空当时 waiting 并 terminate 当时 active，没有关闭状态；close await 期间 run 仍可接新任务，exit/finish 还可调用 _next，产生不属于本次关闭快照的 worker。

WorkerPool 增加 closing/closed；close 一开始阻止新任务和 _next 启动，重复 close 共用同一 Promise。每个 job 独立持有 listener/worker/取消状态，结束一次即清理所有 AbortSignal 和 worker 监听。主进程负责临时产物登记，terminate 后不会执行 worker 内 catch 的情况也能清理/标记恢复；不得删已提交目标。close 完成后所有 Promise 已终态，活动 worker 为零。

图包目前最多 300 MB，在主进程同步 readFile/base64/JSON.parse/JSON.stringify/hash；这里只是有限文件入口，仍足以卡住整个桌面服务。将这些处理交给后台文件任务，IPC 只传文件路径、检查摘要和关系，不回传整包 Buffer。单个任务输出关联还会 indexFile/_metaSync，收藏复制也仍同步：接入已有异步接口，保留数据库写入在主进程，按 C02/C04 状态控制晚到结果。已有轻量小记录可继续同步，避免把所有文件读写都重构一遍。

开发检查：close 与新 run 竞争、排队/运行取消、worker crash、重复 close、临时文件清理、实际打包 worker 依赖；较大图包和图片读写期间主线程心跳持续，事件结果更新正确版本。不要新增测试仅断言“存在 WorkerPool 文件”。
