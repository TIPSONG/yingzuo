## 3. 代码审阅发现

下列路径、行号均指审阅 head。代码变动后以函数名重新定位。P1 表示影响主要功能、状态或数据保护，应先修；P2 表示功能补齐或可靠性问题。

### D01 · P1：真实 Qwen 的提示词绑定没有识别

`shared/bindings.cjs:7,42` 的 TEXT_ENCODERS 白名单不包含 `TextEncodeQwenImage21`。真实图的 positive/negative 上游因此找不到编码器，`inferBindings` 不返回提示词绑定，批量替换提示词等功能被禁用。现有测试用 CLIPTextEncode 证明的是另一种图。

### D02 · P1：Gemma 连线原文被当成“没有可写输入”

`shared/bindings.cjs:68,111` 只在 `inputs.prompt` 已是字符串时设置 textInput。实际是 `[上游节点ID, 输出序号]`，所以 textInput 为 null。`task-service.cjs:132` 的仅润色原文覆盖及采用结果会拒绝；上游追踪也只猜 prompt/text，不能可靠处理 Primitive 类的实际字段。

本轮用与真实结构一致的最小 API 形状执行了纯函数探针，观察到 `promptBinding=null`、`negativeBinding=null`、`enhancerTextInput=null`，采用结果报“润色节点没有可写入的文本输入”。这不是实际生成测试。

### D03 · P1：异步创作流程重新读取当前标签，可能把 A 的结果用到 B

`desktop/ui/tasks.js:80–97` 从当前图开始润色，等待完成后调用 runCurrent；后者在 45–46 行重新读取 `current.activeId`。等待期间切到另一张 Gemma 图，A 的润色文本可被提交到 B。批量弹窗和参考图选择也有 await 后重新读取当前标签的路径。

### D04 · P1：自定义表单保存了，但正式参数表单没有消费它

`template-service.cjs` 提供 formDraft/saveForm；`shared/form-schema.cjs` 有 applyForm。但 templates.open 只传图和 templateId；`desktop/workbench.js:56–68` 仍直接枚举全部节点 widget。正式运行也没有调用 applyForm。修改中文名、分组、顺序、显示字段不会作用到实际创作表单，属于程序链路缺口。

### D05 · P1：维护失败仍无条件启动服务和继续队列

`desktop/maintenance/transaction.cjs:93–96` 的 finally 不区分 done/restored/restore-failed，都会 startService 和 resumeSubmissions。恢复失败留下不完整环境时也会继续使用它。

本轮通过不写文件、不运行真实服务的依赖注入探针得到 `status=restore-failed`，调用仍为 `pause → stop → start → resume → unlock`。

另一个问题：resumeSubmissions 直接调用 queue.resume，它不仅恢复维护前状态，还把用户暂停／重启暂停的任务重新 queued。维护结束不是用户点击“继续生成”。

### D06 · P1：“继续恢复”绕开初次恢复的运行保护

`maintenance-service.cjs:109–120` 的 restoreBackup 检查外部服务、暂停队列、等待、停止 owned 服务；resumeRestore 只取得锁就直接 restore.resume。Windows 下选择继续恢复时可能仍有服务占用文件，或与绘图同时进行。

维护检查也只看服务 ownership 与本应用 activeTasks；**本应用拥有的 ComfyUI 内正在运行外部客户端任务**，并不等于可以停止。必须检查实际后端 queue，保护外部任务。

### D07 · P1：补丁冲突后回到干净目标版本，事务仍记成功

`desktop/maintenance/plugin-ops.cjs:93–108` 重放补丁失败后 checkout/reset 到目标提交，仅把 patchFile 放进 pending；check 只比较 HEAD，事务返回 done，随后重启和恢复队列。补丁文件保留不等于本地功能仍在运行；Gemma 补丁可能暂时被移除却按正常更新完成处理。

### D08 · P1：启动恢复没有启动后端存量任务的持续跟踪

`desktop/services/task-service.cjs:167` 的 start 只 connectSocket/recoverOnStartup，没有启动 follow/pump；main 对 start 也没有 await。存量运行任务核对为 running 后，若不新增任务或点继续，history 完成和作品关联可能不会被主动追踪。启动恢复未完成时也存在接受新任务的竞态。

### D09 · P1：取消后退出最多等 15 秒，然后当作可以退出

`task-service.cjs:163` 吞掉 cancel 错误，再 Promise.race 等待空闲或 15 秒 timer；超时后正常返回。`api.prepareQuit` 与 main.requestQuit 因而继续停止服务／退出，即使任务并未终止。必须把取消请求、已取消、状态未知、确认可退出区分开。

### D10 · P1：目标中断支持未探测，旧版本可能中断下一项任务

`queue-service.cjs` cancel 先读 queue，再发送带 prompt_id 的 `/interrupt`，注释承认旧后端忽略该字段。检查与发送之间任务切换时，全局中断可能落到下一项外部任务。当前本机源代码有针对 job 的取消能力，但客户端没有使用能力分支。

### D11 · P1：服务归属与停止确认不够严格

`comfy-process.cjs:97–104` 强制停止后未再次确认退出，忽略 killImpl 的失败结果，删除 registry 并返回 stopped。stop 失败与 files-in-use 风险被隐藏。

`lmstudio.cjs:59–64` 只凭持久化 serverOwned 布尔值停止；服务被外部重新启动后，旧标记仍可授权停止新的外部服务。CLI 端口也没有与配置地址绑定。Comfy registry 缺 startTime 时仍可能只按路径判 owned，应采取保守策略。

### D12 · P1：模型移动未与任务／维护原子互斥

`maintenance-service.cjs` moveModel 检查一次 activeTasks 后复制、hash、删源，不取得环境锁或 GPU 使用保护。hash/copy 的 await 期间可以开始任务或更新；外部客户端加载模型也未核对。安全移动不能只靠按钮点击时的一次状态判断。

### D13 · P2：分享 JPEG 的元数据过滤没有遍历完整容器

`desktop/core/image-meta.cjs` 的 jpegSegments 在第一次 SOS 返回，stripJpeg 原样附加余下字节。多扫描 JPEG 或扫描后标记区域中的 COM/APP 元数据没有被处理；同时 APP1 的 Exif orientation 被清掉，却没有处理显示方向。现有“容器字节不重编码”测试不证明分享副本没有隐私信息且显示一致。

### D14 · P2：续传 206 分支没有核对旧文件身份

`online/downloader.cjs:114–127` 对 206 只核对 content-range 起点，没有比对保存的 ETag/Last-Modified 与返回值；也允许没有稳定 revision/验证器/hash 的旧 .part 继续追加。来源错误地返回变化后的等大小内容时，无 expectedHash 路径可能完成混合文件。需实现可靠续传或从零重下。

### D15 · P1：任务快照没有隔离敏感节点输入

`TaskRepository/SnapshotStore` 将完整 UI 图和 API prompt 原样写入 JSON。已存在的 Gemma 节点有 `lmstudio_api_key` 字段；用户填写后，这个明文输入会跟随快照保存。CredentialStore 加密应用设置里的凭据并不能保护此路径。正式表单也应保留 password 控件属性，避免变成普通文本框。

这项是由源码输入到存储路径确认的风险，没有读取或使用用户真实密钥。修复不得在测试／交接中使用真实凭据。

## 4. 交接中提到的三点怎么处理

1. **Gemma 不是全部未知。** 真实类名、forceInput 和输入图像字段已从本机读到。下一轮改成显式节点适配与真实结构夹具，不继续只用猜测的 CLIPTextEncode/image1/image2 证明通过。
2. **不调用 ComfyUI-Manager 本身不是缺陷。** 原计划允许受限 Git 后端；保留这个实现，补事务、版本固定和健康检查即可，不为“凑任务完成”安装 Manager。
3. **环境恢复和应用数据恢复应该分开。** 在线修改自己的活动 SQLite 不安全，但不等于无需应用数据备份。要增加一致性导出与退出后恢复机制，覆盖工作区、模板、任务快照、素材引用和数据库。回收区清理则作为独立空间管理任务，不能误删原图／模型／在用备份。

其他程序缺口：自定义参考图关系仍主要放 localStorage，没有进入 WorkspaceTab；重启恢复、复制草稿及跨设备备份因此不完整。真实 SaveImageAdvanced 未适配默认输出规划，workflowId 使用 tabId 会随重开／复制变化。批量 UI 缺参数变化入口。索引、分享导出和备份仍有大量主进程同步 I/O。这些都纳入下面计划。

### 第一批：先保护环境和任务

#### R01 · P1 · 维护状态与暂停租约

修改 transaction.cjs、task-service.cjs、queue-service.cjs：区分用户暂停、重启恢复暂停、维护暂停、退出暂停，使用 reason/token/lease，释放维护 lease 不代表用户 resume。只有成功完成或完整恢复并通过健康检查才允许恢复维护前 owned 服务。restore-failed/needs-resolution 保持阻断，不自动启动或恢复生成。waitForIdle 的 timeout/cancel 参数要贯穿各层，超时返回可读错误，不能当前接口接收参数但内部忽略。

开发检查：维护前用户暂停仍暂停；重启 paused 任务不变 queued；恢复失败不调用 start/resume；成功和完整回滚按原状态恢复；健康检查失败保持阻断。

#### R02 · P1 · 首次／继续恢复走同一保护入口

统一 restoreBackup、resumeRestore 与维护事务的 gate：核对真实后端 queue、ownership、暂停提交、等待任务终止、确认进程退出，再改目录。正在处理外部任务时阻止维护。继续恢复重新验证备份内容和 journal；校验 ID、原路径及各文件相对路径，拒绝越界或未登记目标。失败可再次继续，不能跳过保护步骤。

开发检查：外部服务、owned 服务里的外部任务、文件占用、journal 中断、备份被修改、非法 ID/路径；每次 resume 都经过保护。

#### R03 · P1 · 补丁冲突不记为成功更新

重放失败默认恢复原环境，或者停留显式 needs-resolution，禁止重启和继续队列。staging 先验证补丁可重放，再切换；保留未提交、暂存和未跟踪文件。健康检查至少包含目标版本、补丁效果及配置的 Python／关键模块能力，不能只检查 HEAD。所有结果进度和 UI 区分 done/restored/blocked/restore-failed/needs-resolution。

开发检查：Gemma 补丁干净重放、冲突、未跟踪文件冲突、pip 失败、检查失败；测试不能继续把 pending + 干净目标工作区当作正常成功。

#### R04 · P1 · 服务归属与停止闭环

Comfy 停止检查 kill 结果、等实际退出、强停前再次核对身份；失败保留 registry 和准确状态。LM Studio 用可验证的服务启动身份／实例标识与地址记录，不能跨重启仅用 serverOwned 布尔值；无法核实就按 external 处理。CLI 启动端口与配置一致，实际 API 就绪后才记 owned。

开发检查：停止命令失败、进程继续存活、PID 复用、启动时间未知、外部重启 LM 服务、非默认端口；不得误报“已停止”。

#### R05 · P1 · 取消、退出和精确中断

优先支持实际后端的目标 job 取消；旧版不具备原子目标中断时，清晰限制，不能把“极短竞态”当隔离保证。取消后退出等待实际终态；超时／失败显示返回、继续等或明确的风险选择，而不是 timer 到点直接 shutdown。退出操作自身需要阻止新任务。

开发检查：检查后运行任务切换为外部任务、取消接口拒绝、15 秒后仍 running、断连未知、queued/running 两类任务；不可中断外部任务或假报取消。

#### R06 · P1 · 模型移动与全部环境操作共用锁

模型移动、备份清理、插件操作、restore、更新和任务准备使用协调 gate。取得锁后再次核对本地／外部任务及模型使用，不把 activeTasks 的一次检查当锁。跨盘复制写 journal，hash 验证后切换、最后删源；中途退出可恢复，刷新资源索引。

开发检查：复制期间排队、维护期间移动、外部任务、文件被占用、中断和重复目标；原文件只在确定成功后删除。
